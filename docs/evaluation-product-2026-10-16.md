## 一、前端组织：问题不在「单文件」，在「拆分粒度」

### 实测数据

| 项 | 值 |
|---|---|
| 源码文件 | `src/` **35 个 .js**（另有 order.json） |
| 源码总行数 | **42,838 行** |
| 最大块 | `core.js` **8,418 行** |
| 其次 | `render-widgets.js` 3,560 · `ai-tools.js` 2,764 · `ui-ge-integrations.js` 2,623 · `render-overview.js` 2,536 · `ui-global-events.js` 2,340 |
| 交付物 | 单 `agent-workbench.html`，拼回态 **3,446,139 B** |
| 内部构成 | `<script>` **1 块 2.90MB** · `<style>` **5 块 458KB** · 其余（HTML 骨架+标记）仅 **2.5%** |
| 声音 | **仅** `render-widgets.js` 命中 `AudioContext`（无独立模块） |
| CSS 动画 | `@keyframes` 在 `src/*.js` 中 **0 命中** → 动画全在 HTML 内联 `<style>` 里 |

### 结论：当前架构 = 「源码已模块化 + 交付单文件」，用户的问题要重新切分

用户问「是不是整个前端逻辑全在一个 html 上、要不要拆」——答案是**逻辑已经在 35 个源文件里了**，
拼回成单文件是**构建产物的形态**，不是源码形态。所以真正该问的是两件事：

**A. 源码层拆得够不够？——不够。**
- `core.js` 8,418 行是 god module：工具函数 + store + i18n（32 个语言键在 2634 行附近）+
  配置 + 杂项混居。这与本项目在 MAOP 上已经做过的「god module 拆分」是同类债务。
- 动效/动画/声音**没有独立归属**：动画散在内联 `<style>`、声音挤在 `render-widgets.js`。
  用户直觉是对的——但它们该在**源码层**独立（`src/anim-*.js` / `src/sfx.js`），
  而不是拆**交付物**。

**B. 交付层要不要保持单文件？——建议保持，但要认清代价。**

单文件的好处（这个产品的核心得益）：
- **离线可用 + 零部署**： Electron 套壳、gh-pages 直接托管，双击即用；
- **无模块加载/CORS/版本漂移问题**：`file://` 打开也能跑（真机探针全部依赖这一点）；
- **分发即一个文件**：用户拿到 `agent-workbench.html` 就能用，无需服务端。

单文件的代价（要正视）：
- 单一 `<script>` 2.9MB → **首屏解析时间**随内容线性增长（jsdom 单测已见 environment 阶段占总时长很可观）；
- 无浏览器缓存粒度：改一行也要全量失效（有 service worker 缓解，但 SW 本身 24KB 是另一套逻辑）；
- 3.45MB 里 458KB 是 CSS 且**无组织**（5 个 `<style>` 块）——这是可以立刻改善的肥肉。

### 规划建议（前端组织）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | **拆 `core.js`**（8,418 行 → 按职责切 4–5 块，如 `core-store.js` / `core-i18n.js` / `core-util.js`） | 单文件最大债务；拆分是纯搬运，风险低、收益直接 |
| **P1** | **动效/声音独立成源码模块**（`src/anim.js`、`src/sfx.js`），动画从内联 `<style>` 收敛 | 用户直觉正确；后续改动画不必翻 3,446KB |
| **P1** | **CSS 组织**：5 个 `<style>` 块合并为按「基础 / 组件 / 场景 / 动画」分区，加 lint-css-structure 已有约束守住 | 458KB 无分区 = 每次改样式都全局回归 |
| **P2** | 评估「编译产物多文件 + 单文件兜底」双交付（PWA 用多文件吃缓存，Electron/单文件分发用拼回态） | 收益是首屏与缓存粒度，成本是构建链分支；**先做 P0/P1 再评估** |

## 二、命令机制：面板很成熟，缺的是「注册表」

### 实测

| 件 | 行数 | 已具备 |
|---|---|---|
| `src/ui-palette.js` | **267** | 拼音首字母（`pinyinInitials`）、模糊匹配（`fuzzyScoreCore`）、命中高亮、最近使用（`getCmdRecent/pushCmdRecent`）、键盘选择（`updateCmdSel/runCmd`） |
| `src/ui-hotkeys.js` | **35** | **只有一个** `keydown` 监听 |

### 判断

- **命令面板本身是合格甚至超预期的**：267 行里含拼音与模糊两套匹配 + recent，说明这块认真做过。
- **缺的是「规则」而非「能力」**。用户问「有一套严谨的规则吗」——答案是**没有统一注册表**：
  每个命令是零散注册，没有集中声明 `分类 / 别名 / 快捷键 / 生效场景 / 是否高危`。
  于是：① 快捷键体系几乎空白（35 行）；② 用户无法知道「到底有哪些命令」；
  ③ 新功能加命令时无约束，容易与既有快捷键撞车。
- 快捷键**有**（符合「快捷方式调出」的预期），但覆盖极少；面板调出是主路径。

### 规划建议

| 优先级 | 动作 |
|---|---|
| **P0** | 建**命令注册表**（单文件 `src/cmd-registry.js`）：`{ id, label, keys?, scene?, aliases?, danger?, run }`；`palette` 与 `hotkeys` **共用同一份数据源**。副作用直接解决「快捷键撞车」（注册时按 `keys` 查重即报错） |
| **P1** | 把现有散落命令迁进注册表，并补「命令总览」入口（面板里输空即列出全部分类） |
| **P1** | 快捷键从注册表自动生成，设置面板里可查看/改键 |

## 五、AI 与 agent：**能力已经写了，没暴露成体验**；上下文预算是真空

### 5.1 「输入 URL + KEY 一键扫描 models」——能力已存在，缺的是 UI 暴露

实测（`src/ui-global-events.js:121–153`）：

```js
// 先尝试 GET {base}/v1/models（最轻量：仅鉴权）；失败时降级用 chat/completions 探测
r = await fetch(base + "/v1/models", { method: "GET", headers: headers });
// /v1/models 成功：再确认模型名在模型列表里
```

**服务端拉取的能力是真实存在的**——「测试连接」走的正是 `GET {base}/v1/models`，
并且拿到列表后还会校验「用户填的模型名在不在列表里」（不一致时报
`settings.testConn.modelMissing`）。但这条链路目前**只服务于校验**：填错了才告诉你错了，
没有变成「填完 base+key → 一键拉取 → 下拉挑模型」这个**正向交互**。

> ⚠️ **勘误（2026-10-16 20:00，自己揪出的引用错误）**：本报告初版曾把 `src/ai-tools.js` 的
> `listModels()` 当作"服务端拉取"的证据，**引错对象**。重读后确认 `listModels()` 返回的是
> **本地已配置的 `cfg.profiles`**（供下拉切换 profile），与 `/v1/models` 无关；
> 真正的服务端拉取只有上面 `ui-global-events.js` 这一处。**结论不变**（能力存在、未暴露成体验），
> 但证据链换成正确的那个。留此一条，免得后来的人照着错的引用去找。

**判断：这是体验债，不是能力债。** 用户想要的东西，八成已经在代码里躺着了。

### 5.2 上下文压缩 / token 控制——真实真空

全仓 grep `上下文预算 / contextBudget / maxTokens`：**合计 3 处命中**，全部集中在 RAG 注入一段
（`ai-tools.js:2205` 的「受上下文预算限制…未注入」提示 + `core.js:2636/2637` 的语言键）。
**agent 侧（`ai-loop.js` 625 行）完全没有 token 预算、没有压缩、没有用量可观测。**

现状的 agent 形态（实测 `ai-loop.js`）：
`chatOnce(messages, {tools})` → 流式解析 `delta.tool_calls` → 工具执行 → 结果回流 messages。
这在架构上就是 **OpenAI function-calling 循环**（ReAct 的工程等价物：Thought 由模型自己产出，
Action 是 tool_call，Observation 是工具结果回流）。

### 5.3 架构抉择：建议**不上 Plan-execute**

用户问 ReAct / Plan-execute 如何抉择。基于现状的判断：

- **现在已经是 ReAct 等价物**（tool-calling 循环）。问题不在循环形态，而在**没有护栏**：
  没有 token 预算 → 长会话必然爆；没有上下文压缩 → 记忆/RAG/历史无限增长；没有工具白名单
  → 模型能调的一切都可调。
- **Plan-execute 是复杂度跳变**（要先产出计划、再执行、还要处理计划与现实的偏差），
  对一个**单文件前端 + 可选后端**的产品是过度设计，收益（可预期性）抵不上成本
  （失败模式更多、更难调试、token 更贵）。**不建议。**
- **该做的是把 ReAct 循环的护栏做实**，收益远高于换架构。

### 规划建议

| 优先级 | 动作 | 说明 |
|---|---|---|
| **P0** | **把 `listModels()` 暴露成一键扫描**：填完 base+key → 「扫描模型」按钮 → 下拉填充 → 用户改一个即可 | 纯前端交互改造，后端零改动；直接兑现用户诉求 |
| **P1** | **上下文预算三件套**：① 发送前统计 messages 的 token 估算并展示；② 超预算时的**可配置策略**（截断 oldest / 摘要压缩 / 拒绝发送并提示）；③ 每轮 usage 落盘可查 | 把 3 处命中扩展成真正的预算机制 |
| **P1** | **工具白名单 + 高危工具确认**：哪些工具模型能调、哪些必须用户确认（现有 WebDAV「上传/覆盖」已有确认范式可复用） | MAOP 上做过同类，模式可迁移 |
| **P2** | 每轮 `usage`（prompt/completion/total tokens）进设置面板的「本次会话消耗」 | 可观测性是所有优化前提 |

## 七、UI：用户说「别扭」——那是因为缺可测的标准

用户原话「很多地方看了别扭，但不知道怎么陈述」。这是**没有可测量标准的典型症状**——
别扭是真实的，但缺语言。给他一套企业级可测清单，让他（和我）能指哪打哪：

### 建议采用的判定标准（业内现成可查）

| 维度 | 判定 | 工具 |
|---|---|---|
| **对比度** | 正文 ≥ 4.5:1、大字 ≥ 3:1（WCAG AA） | 项目已有 `lint-colors.mjs`，**先跑一次看它守到哪** |
| **触达目标** | 可点元素 ≥ 44×44（移动）/32×32（桌面） | 一次性脚本扫 `#id` 的最小盒 |
| **状态可见** | 每个操作必须有 成功/失败/进行中 三态可见，失败必须给可执行动作 | 对照 `webdav` 的 401 提示（那是本项目**做得好**的样板） |
| **空态/加载态/错误态** | 每个列表与面板都要有，且不能是空白或「无数据」三个字 | 人工走查 + 截图 |
| **信息层级** | 一屏一个主任务；次要操作沉到二级 | 截图逐屏判 |
| **一致性** | 同类控件同形态（按钮/开关/下拉），图标一套（P0 规则） | `lint-icons.mjs` 已有 |

### 「别扭」最可能的三个来源（基于已见证据的推断，待实测确认）

1. **信息密度失衡**：`render-widgets.js` 3,560 行 + `ui-global-events.js` 2,340 行，
   面板/抽屉类交互极重 → 一屏塞多个主任务是「别扭」最常见来源。
2. **动效无统一节奏**：动画散在内联 `<style>`、无独立模块、无统一时长/缓动规范 →
   潜意识里觉得「不整齐」。
3. **状态可见性不齐**：有的操作诚实提示（WebDAV 401、AI 通道失败缓存），
   有的可能静默——**静默的几处就是「觉得哪里不对」的来源**。
