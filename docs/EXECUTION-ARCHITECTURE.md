# Agent 工坊 · 架构与交付决策（执行定稿）

> 状态：**拍板通过（2026-08-27）**。本文档是后续批次的唯一执行地图。
> 生产者：Cline（主 agent）。裁决：用户。

## 0. 本次决策的三条金线（用户拍板）

1. **性能优先** —— 交付形态必须性能最好，不引入重型前端框架（React/Vue 反而更重、更慢、且业务无此需要）。
2. **Q1 由 agent 定夺** → 采用**轻量拆分**：开发期把 3 万行单文件按语义切分成多个静态片段，build 时合并回**唯一交付单文件**。不引入打包器（esbuild/rollup），避免破坏现有 64 个测试文件的注入体系。
3. **Q2/Q3 = C —— 九个集成全部真双向 + 接 OAuth + 后端全跟上**。

## 1. 一个必须钉死的架构约束（速度与正确性的来源）

### 现状（已实测）
- `agent-workbench.html` = 29,961 行单文件，**无后端、无账号**，三种形态共用同一 HTML。
- `electron/main.js` 已有真 http server 段（行 256~314 附近），8124 端口做局域网同步。
- 前端 9 集成：只有 **Notion 真双向**（58 引用/5 同步函数）；Jira/Linear/Slack/飞书/钉钉有 `connect` 无真同步；Google/Outlook/GitHub 未建。
- 纯前端无 OAuth（OAuth2 已在 v1.14 归档）。

### 约束结论
**"9 个全真 + OAuth"需要一个后端来寄存 token、处理 OAuth 回调与 refresh。** 纯前端办不到——这是数学上绕不开的硬条件，不是偷懒。

## 2. 方案定稿（性能最好 + 九真 + 无障碍）

**形态：Electron 内嵌轻后端（轻量、本地、无服务器），不引框架。**

```
┌──────────── agent-workbench.html (交付真相源，性能最好) ─────────┐
│  前端 JS（原单文件继续演进，只做视图+调用）                        │
└────┬────────────────────────────────────────────────────────┘
     │ fetch: /api/integrations/...   (新的集成统一接口)
     ▼
┌─────────────────────────────────────────────────────────────┐
│  electron/main.js（轻量后端层，复用现有 8124 http server）      │
│   ├ OAuth 回调端点  GET /oauth/callback?code&state           │
│   ├ token 仓库      file 加密落盘（AEAD-GCM, safeStorage）     │
│   ├ token refresh   定时刷新，失败降级提示                     │
│   └ 9 集成调度      统一适配层 → 各 provider 拉到本地/推到远端    │
└─────────────────────────────────────────────────────────────┘
```

**为何这是"性能最好"**：
- 前端仍单文件无框架 → 首屏最快、PWA 最省、现有测试 64 文件零迁移。
- 只在 Electron 壳内多一层本地服务，页面不用轮询，走 IPC 轻调用。
- OAuth token 不落前端 localStorage → 安全更好。

**为何不用重后端（Node/云）**：
- 会引入部署运维、域名、callback 公网路由——工期翻倍，且产品是"本地优先"。
- Electron 内嵌服务已足够承载 9 集成 + OAuth + refresh。够用、快、稳。
