### R-19 [P2·观测面] 设备密钥「写了但没落住」两处完全不说；⑧ 的定性顺带查清

- **起因**：装机探针 ⑧ 在打包态读到 `getDeviceKey()` 有值、`__dk_v2` 却不在 IndexedDB 里，且诊断里
  一条相关的都没有。这条悬了很久（前一批记为"未解释"），本批查清 —— **它是真缺陷，不是探针产物**。
- **根因不在我看到的这两处，且已被并行会话修掉**：`registerDkIdbHelpers` 的接线从来没发生 ——
  SRC 块序实测 `data-idb` 第 2 块、`crypto` 第 10 块（data-idb **先**加载），于是 data-idb 里那句
  `if(typeof registerDkIdbHelpers === "function")` 恒为 false → `_dkIdbGet/_dkIdbPut` 停在默认实现
  （返回 null / false）→ 设备密钥**每次加载重新生成**，旧密文永久解不开。
  **v3.7.95 已按相反方向补接**（`src/crypto.js:22` 起那段注释就是它的交付说明，含"真 Chromium 连续两次
  加载导出的 raw 密钥不同"的实测）。我的探针跑的是 **3.7.93 的产物**（落后 30 个版本），
  所以 ⑧ 检出的是**已修缺陷的旧现场** ⇒ 该条必须在 CI 的新 `win-unpacked` artifact 上复验才算关。
- **本批补的是剩下那半条命：写失败不许再静默**。两处 else 此前什么都不做：
  · 新生成分支：`await _dkIdbPut(...)` 后既不验证也不报错 —— 没落住就等于下次启动换一把新键；
  · 旧键迁移分支：`if(ok && 回读一致) 删旧键` 的 else 什么都不做 —— H3 的安全意图
    （密钥优先进 IDB 以缩小 XSS 泄露面）静默落空，密钥一直躺在 localStorage。
  现在各留一条诊断（`getDeviceKey:persistNew` = error，`getDeviceKey:migrate` = warn），
  并**刻意不加自动兜底**：回退 localStorage 会把 H3 特意换来的安全姿态又输回去，那是产品决策不是兜底。
- **两条实现事实（写用例时踩出来的，值得留着）**：
  1. `registerDkIdbHelpers` 把 putFn 包成 `.then(()=>true).catch(()=>false)` —— 所以
     **`_dkIdbPut` 的返回值在生产里不可信**（IDB 不可用时它也回 true），判据只能是**回读比对**。
  2. `initCrypto()` 自己就调 `ensureDeviceKey()`（`crypto.js:252`），而 `_deviceKey` 一旦缓存，
     `ensureDeviceKey()` 首行就 return —— 用例必须按 **reset → 装接缝 → initCrypto** 的顺序装配，
     否则接缝根本没被调用、四条断言全以"没诊断"的形式假失败（我第一版就是这个顺序错）。
- **门禁**：`tests/device-key-idb-persistence.test.js` 4 例（写失败须说话 / 成功路径不许刷诊断 /
  迁移失败时旧键必须保留 / 回读一致才删旧键）。变异 2/2：把新生成分支闭嘴 → 恰好 1 条红；
  把迁移分支闭嘴 → 恰好另 1 条红；还原后 4/4 复绿。

### R-26 [P1·收口 R-9 遗留账] 「空缓存钉死」**已修**，但又查出**另一层**：检索不等回填就返回空

- **缘起**：R-9 那条明写「未修（留待下一批）：改法需先想清『空缓存该不该钉死』与『IDB 未就绪 vs
  确实没有向量如何区分』」。本轮（2026-10-16）去收这笔账，**先核实再动手**。
- **核实结论 1（那条是过时账）**：原缺陷**已在 v3.7.101 修掉**。`src/ai-tools.js:1910`
  `_ragVecCache = { model, map, loaded }` 引入 `loaded` 标志 —— 只在**确实读到 IDB** 时置 true，
  空 Map 不再被钉死、可重试（注释原文即点名「台账 R-9 flaky 的根因」）。v3.7.115 又加了
  `semanticRecallStatus()`，把「悄悄退化成词法」做成用户可见状态（`mode:"idb"` 即"IDB 读不到"）。
  **台账那两个待决问题，代码里已经各自有答案**：不该钉死（`loaded`）、用 `loaded` 区分"未就绪 vs 确实空"。
- **核实结论 2（本机无就绪窗口）**：新造探针 `_probe/rag-reload-window.cjs` 实测「正常刷新 →
  **立即**检索」**5/5 全部召回**（`len=1 / first=doc-auth / via=vec`，`cache={loaded:true,size:2}`）；
  对照「等 2s 再检索」3/3、连检两次 3/3 同样全绿。**证书：本机不存在"刷新后应用就绪窗口"**，
  与 R-9 里那次排除性实验（「刷新后应用就绪窗口不存在」）一致。
- **核实结论 3（真缺陷在这里）**：`ragInit()`（`src/ai-tools.js`）里的有界回填
  **`ragEnsureVectors(20).catch(...)` 是发起即走、没有 `await`**：
  ```js
  if(!(opts && opts.skipBackfill)){ ragEnsureVectors(20).catch(...); }   // ← 未 await
  _ragReady = true; return true;
  ```
  而 `ragSearch` 是 `await ragInit()` **紧接着**就 `ragHybridSearch` → `ragVectorSearch` →
  `const cache = await ragVecLoadAll(); if(!cache.size) return [];` ——
  **回填还在飞，cache 还是空的，于是这次检索直接返回空**（而且连 query 的 embedding 都不发）。
- **重现证据（三层齐）**：
  ① 注入式（qoder 的 `_probe/repro-rag-idb-unready.cjs`）：让 IDB 在启动窗口不可用 → **3/3 复现
  `len=0`**（本轮亲跑：`after={"len":0}` × 3，`embedding增量=1` —— 那 1 次正是回填发起的，
  可作为「回填在跑但检索没等」的旁证）；
  ② 正常态（本探针）：5/5 召回 → 说明缺陷**只在 IDB 不可用/慢的窗口**触发；
  ③ 代码级：上面那段 `未 await` 就是机制本身。
  → 三者合起来解释了 CI 上 `rag-hybrid.spec.js:132` / `workflow.spec.js:91` 的**首跑红、同 commit
  重跑绿**：CI 机器上 IDB 偶发慢/不可用 → 回填未完成 → 断言拿到空 → 红；重跑 IDB 快 → 绿。
- **建议修法（待定夺，本轮**未改代码**）**：给回填补一个「进行中」的 promise
  （如 `_ragBackfillPromise`），让 `ragVectorSearch`/`ragSearch` 在 **`cache.size === 0` 且回填在飞** 时
  **有界等待**（例如 3s 上限）后再判空。这样：IDB 不可用/慢 → 等到回填即可召回（消除 flaky）；
  真无文档 → 回填立即完成，仍返回空（**不误伤**，这正是 R-9 担心的「改错会让正常的空索引每次都重读 IDB」）。
  不动的部分：`loaded` 语义（v3.7.101）与 `semanticRecallStatus` 口径都保留。
- **为什么不直接改**：RAG 在对话主路径上，且"等待时长 / 是否阻塞检索"是产品决策（等待会让首轮回复
  略慢）。按本仓「先造重现再改、产出报告先给人看」的纪律，**报告先行**。
