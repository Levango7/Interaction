## 结尾

如果只要一个定性判断：

- 可相对放心的结论是：这个项目在单文件约束、往返校验、分层结构、槽一致性、卫生类门禁这几块，有较强的自我约束和机器证据。
- 需要保留疑问的结论是：测试套可验性、架构洁净度、动态回归这几项我尚未独立确认。
  （其中「测试套可验性」已于 2026-10-16 复现收敛，见文末「补充」。）

如果你准备据此做下一步决策（继续审计、迁移、接手、发布策略），建议至少补两项：

1. 把测试可验性收敛到最小可复现结论；
2. 单独跑一个行为/回归面（端到端、视觉回归、或核心工具链路之一），不要只靠静态门禁交差。

本文写完时我有两类感受：

- 对“项目有没有工程实质”这件事，我有不少机器复现的锚点；
- 对“那些锚点之外的所有行为是否真的站得住”这件事，我没有足够的闭合证据。

这两者不矛盾。评估的目的不是在两种感受里选一个，而是把它们分开。

## 补充：测试套可验性的最小可复现结论（2026-10-16 复现）

- **全量并行**（`npm test`，本机 32 核 ~31 worker · JSDOM）：**151/152 文件、1714/1725 用例通过**。
  唯一未通过的文件 `tests/cloud-sync-stage1.test.js` 报的是
  `[vitest-worker]: Timeout calling "onTaskUpdate"`（worker RPC 超时），**无任何断言失败**
  （Errors 4，全为同族超时）。
- **同文件隔离单跑**（`npx vitest run tests/cloud-sync-stage1.test.js`）：**13/13 通过，exit 0**。
- **结论**：全量跑的 11 个「未通过」是本机 worker 噪声（`AGENTS.md` R9 已登记的现象），不是产品回归；
  测试套本身可跑、可验，只是不适合在共享树上做无隔离的全量判据。
- 边界提醒：`npm test` 失败时 **`posttest` 不会抽回源码态** —— 跑完全量后必须手动
  `npm run src:extract` 并过 `check:source-state`，否则工作树停在注入态（3.88MB），一旦 `git add` 即污染仓库。
