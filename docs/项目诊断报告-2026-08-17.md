## 0. 结论先行（先看这里）

**一句话诊断：这个项目"代码质量不差"，真正的问题是"结构失控 + 定位模糊"。**

你感觉"问题很多"，但问题不在你担心的"代码写得烂"。相反，代码层面的工程纪律（注释、防御性编程、测试、安全加固）是明显高于平均水平的。

真正的病在三个地方，而且它们互相放大：

1. **单文件巨石**：全部 UI + 逻辑 + 数据塞进一个 28,875 行的 HTML，没有模块、没有框架、没有真正的构建。
2. **产品定位模糊**：一个应用同时想当"任务管理 + 笔记 + AI 助手 + 自动化平台 + 第三方集成 + 习惯养成游戏 + 健康追踪"，什么都要，什么都浅。
3. **文档与代码漂移**：README 一个文件里出现 3 个版本号，接口文档引用的行号是几个月前的。

好消息：这三个都不是"推倒重写"级别的问题，而是"结构决策 + 聚焦取舍"。对一个经验不足的开发者来说，这是**可以逐步解决**的，比"代码烂需要重写"好得多。

## 2. 三个根本病因（比表面症状更重要）

### 病因 A：单文件巨石（最重要）

`agent-workbench.html` 是唯一交付真相源，直接手改。证据：

- CSS 在行 21–2311，JS 从行 3202 起，全部内联在一个文件。
- `scripts/build.mjs` 明说："不再有 src->HTML 字节拼接""`src/modules` 是早期模块化快照、**已落后，不再参与构建**"——也就是说，**曾经尝试过模块化，后来放弃了**，退回直接改单文件。
- 一份重试逻辑在两处重复实现：HTML 里的 `chatOnce` 和 `electron/main.js` 的 chat IPC，代码里甚至留了警告注释："本矩阵与 main.js 为**跨进程双实现（无共享构建管线）**，修改任何一侧前必读…"。
- v1.14 的 CHANGELOG 记录了一次"误删事故"：删企业模块时把 `wfEvalCondition` 条件解析器一并删了，最后"从 HEAD 备份还原"。
- 路线图文档自己也写："单文件 HTML 拼接的分段闭合是**高发坑**"。

**后果**：改一处怕碰坏另一处 → 靠海量测试兜底 → 不敢大改 → 越改越臃肿。这是你"不知道如何下手"的根源：在 28K 行单文件里，任何改动都像在拆一颗炸弹。

### 病因 B：产品定位模糊（"什么都要"）

README 声称的功能面之大，一个应用想同时覆盖：

1. 任务看板（4 场景 × 待办/进行中/已完成）
2. 场景资料库（会议纪要/代码片段/学习资料/生活记录）
3. AI 聊天助手（带 16 个工具）
4. Agent 能力（工作记忆 / 多步目标 / 跨场景协调）
5. 场景联动"习惯链"（带 streak + 热力图 + 动画）
6. 工作流画布 + 自动化规则 + Webhook
7. 九大第三方集成（Notion/Jira/Slack/飞书/钉钉/Google/Outlook）
8. 语音助手
9. 周报生成器、SM-2 间隔复习、健康追踪（运动/体重/睡眠/喝水）

典型信号：
- "生活"场景里塞了健康追踪（运动/体重/睡眠/喝水），这和"任务管理"完全是两个领域。
- "习惯链"规则是拍脑袋的："交付完成→看技术视频""项目上线→吃顿好的"。
- 每个场景的 AI 系统提示词都是泛泛一句（"你是一个专业的办公效率助手…"），没有任何场景深度。

**后果**：没有清晰的"这是给谁、解决什么核心问题"的回答。功能很多，但没有一个做到"好用"的深度。v1.14"做减法"删了 17,000 行（企业协作/CRDT/原生打包）是对的，但减得不够，也暴露了之前"什么都往里加"的惯性。

### 病因 C：文档与代码漂移

- README：标题写 "v1.11.1"，第八节写 "v1.9.5"，而 package.json / manifest.json / 代码 `VERSION` 都是 "1.14.0"。**一个 README 三个版本号。**
- `docs/ai-tools.md`：写 `VERSION = "1.1.0"`，引用行号 1581–1616，但实际 `TOOLS` 在行 5373、`VERSION` 在 3202。**接口文档的行号全是旧的。**
- v1.14 删掉的模块（webhook 总线现在 `webhookEmit` 是 noop、生物识别门禁），路线图里还写着"✅ 已实施"。

**后果**：文档不但不能帮你，还会误导你——按旧行号找代码找不到，按旧版本号判断项目状态会错判。

## 4. 优先级行动方案（给"不知道如何下手"的你）

按这个顺序做，每一步都能独立落地、独立验证，不要贪多。

### 第 1 步：先定"一句话定位"（1–2 天，不写代码）

回答三个问题，写进 README 顶部：
1. 这个产品是给谁用的？（一个具体的人，不是"所有人"）
2. 它解决对方哪个最痛的痛点？（一个，不是十个）
3. 为什么用户不直接用 Notion/滴答清单/ChatGPT？（差异化）

建议先砍功能面。候选定位方向（选一个，别全选）：
- **A. 本地优先的私人任务 + AI 工作台**（隐私是卖点，砍掉集成/自动化/健康）
- **B. 极简习惯链任务养成工具**（游戏化是卖点，砍掉 AI Agent/集成/健康）
- **C. 你的 AI Agent 桌面入口**（AI 是卖点，砍掉习惯链/健康/九大集成）

我的判断：**A 最贴合你已经做好的技术底座**（单文件、纯本地、PWA、Key 加密）。健康追踪、九大集成、工作流画布建议先冻结/归档。

### 第 2 步：冻结范围（0.5 天）

把"第 1 步选定的核心"之外的功能，在代码里标 `/* DEPRECATED */` 并禁用入口，但**先别删**（删代码最容易引发误删事故，v1.14 已经演示过）。用 feature flag 关掉，观察几周没问题再删。

### 第 3 步：先治"文档漂移"（1 天，零风险，立刻止血）

1. README 版本号统一为 1.14.0（现在一个文件三个版本号）。
2. `docs/ai-tools.md` 要么更新行号到当前代码，要么删掉行号、只保留契约描述（推荐后者，行号永远会漂）。
3. 把已删除的模块（webhook 总线、生物识别）在路线图里标"已归档"，别再写"✅ 已实施"。

这一步不碰代码，但立刻让你的认知不被打乱。

### 第 4 步：再动架构（最慢、最值钱，别急着一次到位）

目标是"把巨石拆成能单独理解的模块"，**渐进式**，不是推倒重写：

1. 先把重复实现的 `chatOnce` 重试矩阵抽成一份共享代码（哪怕先放一个 `shared/` 目录，构建时拼接），消除"改一处要改两处"的地雷。
2. 用 ES Modules 或至少 IIFE 分块，把"数据层 / AI 层 / UI 层 / Agent 引擎"物理分开（现在它们混在一个 script 里）。
3. 引入一个真正的构建（Vite/esbuild 任选其一），让 `src/` 成为真相源，`agent-workbench.html` 变成构建产物——**反转现在的"HTML 是源、src 是快照"的关系**。

这一步你会踩坑，但它是唯一能根治"不敢改"的办法。建议每拆一个模块就跑一遍 624 个测试确认没破坏。

### 第 5 步：AI 层"降级重定位"

现在 AI 的"Agent"宣称（记忆/目标/编排）实际很浅：
- 记忆 = 60 条 + 关键词匹配（不是真记忆）
- 编排 = 循环次数 6→12 + 步骤列表（不是真 agentic）

建议：**对外话术降级**，从"Agent"改叫"带工具的 AI 助手"；对内把重点放在"让 16 个工具在真实任务流里更可靠"，而不是堆更多"记忆/目标"这种看起来智能、实际很浅的能力。两条具体改进：
1. 把 `update_task`/`delete_task` 的 `force` 参数显式加进 TOOLS schema（现在依赖 UI 注入，纯 API 调用方没有标准入口，接口文档自己也标注了这个洞）。
2. `add_record.fields` 给每个场景补子 schema，提升模型调用准确率。

---

## 5. 不要动的（别把好牌打烂）

- **测试体系**：624 例 + 门禁是难得的资产，重构时它是你的安全网，别删。
- **设计令牌 / a11y 基座**：这块做得比大多数商业项目规范，UI 不满意的根源在"信息密度/产品"，不在令牌体系。
- **安全加固**（SSRF 校验、IPC 硬化、AES-GCM 加密）：这是加分项，保留。

---

## 6. 给你的总建议

你不是"代码写得烂"，而是**一个人用 52 个 commit 快速堆出了一个没有边界的巨石**。这很正常，而且可逆。关键转折点在于：**从"加功能"切换到"减功能 + 定边界 + 拆结构"**。

如果只能先做一件事：**先做第 1 步（定一句话定位），再做第 3 步（统一文档）**。这两件零代码风险，却能让后面所有决策都有据可依。
