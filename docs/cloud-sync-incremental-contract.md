# 云同步增量：客户端契约提案（v3.7.85）

> **2026-10-10（v3.7.105 批）：阶段 1（C1 + C2）已按本契约交付**，实施记录见 §三 末。
> 阶段 2 起仍然后端前置 —— 服务端已从孤立提交找回并加固（`docs/backend-recovery-assessment.md`），
> 但其 `server/src/sync.js` 明确"刻意不做增量 / 水位 / 冲突合并"，与本契约 §二 口径一致。

> 结论先行：**这项不是"客户端再做一版就能上"的东西** —— 现有协议是「全量快照 + last-write-wins」，
> 真正缺的后端能力（增量水位、逐键变更清单、冲突策略）在本仓之外。本文档把**客户端侧能独立完成的
> 部分**与**必须等后端的前置条件**分开列清，作为后端立项时的接口输入；单改客户端不产生任何用户价值
> （只会引入"看似增量、实则丢数据"的假象）。

## 一、现状盘点（客户端，实测口径）

| 项 | 现状 |
|---|---|
| 上行 | `apiPutSnapshot(_buildCloudSnapshot())` —— **全量**键值快照（已排除密钥/本机控制键，v3.7.58） |
| 下行 | `apiGetSnapshot()` → `_applyCloudSnapshot()` —— 覆盖式写入 + 任务按 `updatedAt` 合并（v3.7.80） |
| 冲突 | **last-write-wins**，无冲突检测、无版本号、无操作日志 |
| 保护 | 覆盖前写 `pre_restore_backup` 本机回滚档（v3.7.52） |
| 重试 | 5xx/429 退避 2 次（v3.7.73）；errKind 分类提示（v3.7.71） |
| 成本 | 全量快照随数据线性增长；小改动也要传全量（弱网/移动端体验差） |

## 二、后端需要提供什么（**前置条件，本机不可解**）

1. **增量水位**：客户端上行带 `since=<上次成功同步的水位 token>`；服务端据此返回
   `{ base, changed: [{k, v, ts}], removed: [k...], token: <新水位> }`。
   —— 水位须**单调且服务端权威**（不能用客户端时间戳当水位）。
2. **删除信号**：现行全量协议靠"键消失"表达删除，增量必须有显式 `removed` 列表。
3. **冲突策略开关**（服务端侧）：至少 `lww`（保持现状）与 `mv+提示`（三路合并/冲突清单下发）两档。
4. **幂等键**：同 `token` 重放必须幂等（移动端重试是常态）。

> C1–C4 的实现纪律同本仓惯例：**接线点留好、UI 不承诺、守护钉死"开关关闭时行为零变化"**。

### 阶段 1 实施记录（2026-10-10 · v3.7.105 批）

| 项 | 落点 | 口径 |
|---|---|---|
| C1 记录器 | `src/data-rw.js`：`_chlogRecord(k, op, payloadStr)` + `getSyncChangelog()`，队列键 `PREFIX+"sync_changelog"` | 上限 **500**（溢出丢最旧）；`h` = `fnv1aHex(序列化值)`（弱哈希，仅判"变没变"，不承载安全语义） |
| C1 接线点 | `save()`（op:"set"，复用其序列化结果，不二次 stringify）+ `_sharedSafeLSRemove()`（op:"del"，**删前存在且删除未抛错才记** —— 对不存在的键 removeItem 是静默 no-op，记了就是假信号） | 本仓业务数据的"删除"多为数组重写（走 save），两条路径合起来即同步面变更的来源 |
| C1 门控 | **C4 开关 `cfg.syncIncremental`（默认关）**，经 `getCfg()` 活缓存读取（与 `saveCfg` 的缓存更新惯例同源） | 关闭时 `_chlogRecord` 首行返回 —— **零行为变化**，由 `tests/cloud-sync-stage1.test.js` 逐项钉死（含配额 / 读失败注入） |
| C1 不上云 | `render-overview.js` 的 `SYNC_EXCLUDED_KEYS` 加入队列键 | 队列是本机变更时间线：上云无跨端收益（隐私面），且会让"原料"自指 |
| C2 记录 | `apiPutSnapshot()` **发送前**记 `lastPushBytes / lastPushKeys` 进 `sync_meta` | **失败也记**：413 / 弱网下用户要看的是"这次要传多大"；字节口径与后端一致 = **只算 snapshot 的 UTF-8**（不含 `updatedAt` 包装），对齐 `server/src/sync.js` 的 `MAX_SNAPSHOT_BYTES` |
| C2 展示 | 设置面板行 `#apiPushSize`（更新走既有 `_renderLastSync()`）+ `buildDiagReport()` 云同步行 | 面板行 i18n 键 `api.pushSize / api.pushSizeVal`（中英各一） |

**已知边界（如实记账）**：

- `op:"del"` 覆盖 = 经 `_sharedSafeLSRemove` 的删除（集成配置摘除 / `rec_` 资料键 / `push_subscription`）；
  `src/data-links.js` 的 `resetCustomLinks()` 是**裸 `removeItem`**，其既有语义是"存储异常仍抛出"，
  改走安全删除会引入与本批无关的行为变化 —— 为守"零行为变化"纪律**未接**，留阶段 2 与协议一并收口。
- 队列是"原料"不是增量协议：**阶段 2 落地前，任何上行仍是全量**（防"看似增量、实则丢数据"）。

## 四、分阶段建议

- **阶段 1（后端未就绪）**：C1 + C2 ✅ **已交付（v3.7.105 批）** —— 纯客户端、零协议变更、无用户可见风险。
- **阶段 2（后端契约落地）**：上行切增量（开关制），下行保留全量回退（服务端不支持水位时自动降级）。
- **阶段 3**：C3 冲突计数 + 下行也切增量；两端都按水位，冲突策略由服务端下发。

## 五、为什么现在不写增量代码

- 没有服务端水位实现 → 客户端"增量上行"只能退化为全量（假增量）；
- 冲突策略没定 → 客户端先定 LWW 之外的策略，等于把产品决策埋进协议；
- 历史上本仓已经吃过一次"stub + 活 UI = 虚假功能"的亏（离线AI/ML预测等 4 子系统，v3.7.58 清仓）。
  宁可**如实记账**（本文档 + product-scope 路线余量④），不做占位增量。
