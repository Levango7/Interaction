# 云同步增量：客户端契约提案（v3.7.85）

> **2026-10-10（v3.7.105 批）：阶段 1（C1 + C2）已按本契约交付**，实施记录见 §三 末。
> 阶段 2 起仍然后端前置 —— 服务端已从孤立提交找回并加固（`docs/backend-recovery-assessment.md`），
> 但其 `server/src/sync.js` 明确"刻意不做增量 / 水位 / 冲突合并"，与本契约 §二 口径一致。

> 结论先行：**这项不是"客户端再做一版就能上"的东西** —— 现有协议是「全量快照 + last-write-wins」，
> 真正缺的后端能力（增量水位、逐键变更清单、冲突策略）在本仓之外。本文档把**客户端侧能独立完成的
> 部分**与**必须等后端的前置条件**分开列清，作为后端立项时的接口输入；单改客户端不产生任何用户价值
> （只会引入"看似增量、实则丢数据"的假象）。

## 一、现状盘点（客户端，实测口径）

| 项 | 现状 |
|---|---|
| 上行 | `apiPutSnapshot(_buildCloudSnapshot())` —— **全量**键值快照（已排除密钥/本机控制键，v3.7.58） |
| 下行 | `apiGetSnapshot()` → `_applyCloudSnapshot()` —— 覆盖式写入 + 任务按 `updatedAt` 合并（v3.7.80） |
| 冲突 | **last-write-wins**，无冲突检测、无版本号、无操作日志 |
| 保护 | 覆盖前写 `pre_restore_backup` 本机回滚档（v3.7.52） |
| 重试 | 5xx/429 退避 2 次（v3.7.73）；errKind 分类提示（v3.7.71） |
| 成本 | 全量快照随数据线性增长；小改动也要传全量（弱网/移动端体验差） |

## 二、后端需要提供什么（**前置条件，本机不可解**）

> **2026-10-10 交付说明**：本节原为「后端立项时的接口输入」清单；**已于 v3.7.106 在本仓
> `server/` 内落地**（`POST /api/sync/changes`，实现即口径：`server/src/store.js` 的「增量同步」段 +
> `server/src/sync.js` 的路由注释；真机验证 `server/verify/incremental-check.cjs` 38 项）。
> 落地时对原设计做了三处**定稿**（见下方 【定稿】），其余按原文照做。

1. **增量水位**：客户端上行带 `since=<上次成功同步的水位 token>`；服务端据此返回
   `{ base, changed: [{k, v, ts}], removed: [k...], token: <新水位> }`。
   —— 水位须**单调且服务端权威**（不能用客户端时间戳当水位）。
   **【定稿】**：`base` 字段不引入（响应即 `{token, changed, removed, needsFull}`）；
   `removed` 从 `[k...]` 定稿为 **`[{k, ts}]`** —— 下行删除要参与客户端侧的 LWW 判定
   （本机有更晚未上传变更的键不删），没有 ts 判不了。
2. **删除信号**：现行全量协议靠"键消失"表达删除，增量必须有显式 `removed` 列表。
   **【定稿】**：删除用 **tombstone**（`tomb[k]={ts,seq}`），超 200 条丢最旧并推进
   `prunedBelow`；客户端 `since < prunedBelow` → 响应 `needsFull:true` → **回退全量**。
3. **冲突策略开关**（服务端侧）：至少 `lww`（保持现状）与 `mv+提示`（三路合并/冲突清单下发）两档。
   **【定稿】**：本版**只做 lww**（逐键、`ts` 大者胜、**ts 相等时删除胜**）——
   `mv+提示` 属产品决策，未定不做（照 §五 的纪律：不把产品决策埋进协议）。
4. **幂等键**：同 `token` 重放必须幂等（移动端重试是常态）。
   **【定稿】**：幂等落在**写侧**——同 `(k, v, ts)` 重放不改状态、水位不动（无需另立幂等键）。

### 阶段 2 实施记录（2026-10-10 · v3.7.106 批）—— 增量上行 + 下行增量，开关制 + 全量回退

**服务端**（`server/`，真机验证 `verify/incremental-check.cjs` **38/38**）：

| 件 | 落点 | 要点 |
|---|---|---|
| 端点 | `POST /api/sync/changes`（`src/sync.js`） | 单次往返 = 上行 `{since, changes:[{k,v,ts}], removed:[{k,ts}]}` + 下行 `{token, changed, removed, needsFull}`；Bearer 鉴权；坏输入 400 |
| 逐键视图 | `store.js` `_incr` / `mergeIncremental` | `keys[k]={v,ts,seq}` + `tomb[k]={ts,seq}` + **服务端权威水位**（`seq=++watermark`，token=水位）；LWW：ts 大者胜、**相等时删除胜**；幂等：同 `(k,v,ts)` 重放不改状态 |
| 剪枝与回退 | `store.js` `_pruneTomb` | tombstone >200 丢最旧、推进 `prunedBelow`；`since < prunedBelow` → `needsFull:true` → 客户端回退全量 |
| **快照相干性** | `setSnapshot` → `_rebuildIncr` | 全量 PUT = **重建**逐键视图（每键取新 seq、消失键补 tombstone）；增量写 = **逐键补丁**同一份快照记录 —— 「一台走全量、另一台走增量」必须同世界（本项是设计里最容易坏的一环，脚本第 ⑦⑧ 组专门钉） |
| 元键 | `_isMetaKey` | `_` 前缀（`_deviceMeta` 等）不进逐键视图 |

**客户端**（`render-overview.js` / `ui-ge-api.js` / `data-rw.js`，单测 `tests/cloud-sync-stage2.test.js` **11 例**）：

| 件 | 落点 | 要点 |
|---|---|---|
| 分流 | `syncRound()` ← `doSync` | 开关关 = **逐位全量**（零行为变化，测试钉死"无 /changes 调用"）；开关开 = 增量 |
| delta 折叠 | `_buildSyncDelta()` | 从 C1 日志取每键最新一条；范围过滤三处同口径（`_inSyncScope` = 出站/入站/增量键集一致）；`set` 但键已不在 → 按删除 |
| 游标 | `syncToken` 落盘 + **成功即清日志** | 所有当前值已上行 + 远端更新已应用 ⇒ 收敛后清空是最简单且正确的游标（免环形队列位点维护） |
| 下行 | `_applyCloudSnapshot(changed对象)` + 裸删 `removed` | changed 走快照同一应用路径（任务合并/回滚档/广播全复用）；removed **裸删**（远端删除不是本地变更、不入日志），本机有更晚未上传变更的键跳过 |
| 回退 | `404/405` 与 `needsFull` → `"full-fallback"` | 旧部署或水位太旧 → 全量 PUT（服务端顺带重建增量视图） |
| 看板 | C2 同栏记 **delta 体积** | 增量轮的行含义="本次要传的增量有多大"，口径写在看板注释 |

**已知边界（如实记账）**：
- 冲突策略只有 `lww`（逐键、删除胜平局）；`mv/三路合并` 未做（产品决策，见 §二.3 定稿说明）。
- 响应会**回显**本轮刚上行的变更（客户端应用为幂等 no-op）—— 换取"冲突时服务端权威值自动回流"；
  大 delta 时往返体积翻倍，后续可加 `echoPolicy` 精化（未做，先保正确性）。
- 客户端日志上限 500 条（C1）——足够覆盖两次同步之间的变更；溢出丢最旧，属"原料"丢失，
  由水位回退兜底（落后太多 → needsFull → 全量）。

### C3 实施记录（2026-10-10 · v3.7.107 批）—— 冲突计数（静默 LWW 的可解释出口）

- **口径**（决定数字可不可解释）：`lastPullCover` = 本次下行**真正改动本机键值**的数量 ——
  本机有值且与远端值不同才计入；远端新增键（本机无值）、值相同的键、被「本机更晚变更」保护
  跳过的远端删除，**均不计**（后两类本就没动本机数据）。
- **落点**：`_applyCloudSnapshot`（全量 / 回退 / WebDAV 三路共用）返回并记录 changed 侧计数；
  增量轮把 removed 侧（删除的键里本机原有值的）相加后写回 `sync_meta.lastPullCover`
  —— **每轮都写**（无下行 = 0，面板显示「无」），与「上次上传体积」同口径：永远是"最近一次"的实况。
- **展示**：设置面板行「上次云端覆盖」（`#apiPullCover`）+ `buildDiagReport` 同源行。
- **测试**：`tests/cloud-sync-stage2.test.js` §C3（5 例：全量口径边界 / 无覆盖显示「无」/
  changed+removed 相加且剔除本机无值 / 保护跳过不计 / 诊断行同源）。

### 阶段 3 实施记录（2026-10-10 · v3.7.108 批）—— 下行按需增量拉取

- **缺口**：阶段 2 的下行变更只在上行时捎带回来（变更日志为空就不轮询）—— 跨设备的改动要等本机
  下一次编辑才可见。
- **做法**：`render-overview.js` 加载即挂 5 分钟定时拉取；`_syncIncrementalPullTick` 抽成命名函数
  （生产里是 `setInterval` 回调、测试里直调），**仅**在「已登录 · 增量开关开 · 本会话未发生过
  "服务端不支持"回退」三者同时成立时跑；走既有 `window.doSync`（自带状态机），不新增错误语义。
  开关关 / 未登录 / 不支持增量时一律不跑 —— **开关关时逐位零行为变化**。
- **刻意不碰 `ui-ge-api.js`**：那是并行会话在途的文件（凭据密封批次③）；定时器建在本块 + 走
  `window.doSync` / `window.isApiLoggedIn` 桥（与 `cloudCheckOnLogin` 同款用法）—— 两个会话的改动
  不混进同一文件（并行协作的铁律）。
- **测试**：`tests/cloud-sync-stage2.test.js` §阶段3（4 例：开关关零行为 / 未登录不请求 / 无上也拉 /
  回退后不再打扰）。**坑留档**：vitest 的假时钟只覆盖**测试 realm** 的计时器 —— 页面脚本
  （jsdom realm）里建的 `setInterval` 收不到时间推进（实测：测侧自建间隔触发 360 次、页面里建的 0 次），
  故抽命名 tick 直调而非推假时钟。
- **冲突策略**：仍只有 `lww`（逐键、ts 大者胜、相等删除胜）；「由服务端下发」与 `mv/三向合并`
  属产品决策，未定不做。

### 阶段 3 之二：mv+提示 实施记录（2026-10-10 · v3.7.109 批）—— 冲突策略由服务端下发

**定稿**：默认 `lww`（输了的一方静默丢弃，现状零变化）；`cfg.sync.conflictPolicy = "mv"` 时，
输了的一方**不再静默丢弃**，而是记进冲突清单随 `/api/sync/changes` 响应下发，由客户端处理。
服务端**不替客户端合并**（合并语义在客户端 —— 单边做会造成「后端以为在合并、客户端以为被覆盖」）。

- **服务端**：`store.js` 逐键检测（`cur.ts > ts` 或同刻不同值 → 记 `{local, remote, at}`，
  上限 50 条丢最旧；新值落定即清该键冲突）；`POST /api/sync/resolve {k, choice, ts}`
  （choice = `local` | `remote`，ts 由客户端提供且必须新于双方）；响应带 `conflictPolicy` 声明。
- **客户端**：任务键**结构化自动合并**（两版数组按 id 合并、updatedAt 大者胜 —— 与
  `_applyCloudSnapshot` 同口径；合并结果以新 ts 上行 → 服务端冲突自动作废）；其余键
  **不猜**，列在「设置 → 账号 → 云同步」的冲突面板上让用户「保留本机 / 使用云端」二选一。
  `lww`（默认）下清单恒空、整段不触发。
- **验证**：`verify/incremental-check.cjs` ⑫ 组（重启换 mv 机 15 项：声明 / 冲突记录与双方值 /
  未被覆盖 / 双向 resolve / 清空 / 非法 choice 400 / 已解决再解决 404 / 无 token 401），
  **54/54**；客户端 `tests/cloud-sync-stage2.test.js` §mv（5 例），定向 45/45。
- **已知边界**：冲突清单上限 50 条（溢出丢最旧，客户端下轮全量再对）；`v:null` 表示「本机选择
  删除」的冲突同样走同一清单；服务端不做任何自动合并。

## 五、为什么当时不写增量代码（历史注记 · **2026-10-10 已解**）

> 本节保留为决策史：理由是"**客户端单边**做"才会成立的 —— v3.7.106 批把服务端（`server/` 在本仓内）
> 与客户端一起升级，前提条件已满足，阶段 2 已交付（见 §三 实施记录）。下列判据本身仍然有效。

- 没有服务端水位实现 → 客户端"增量上行"只能退化为全量（假增量）；
- 冲突策略没定 → 客户端先定 LWW 之外的策略，等于把产品决策埋进协议；
- 历史上本仓已经吃过一次"stub + 活 UI = 虚假功能"的亏（离线AI/ML预测等 4 子系统，v3.7.58 清仓）。
  宁可**如实记账**（本文档 + product-scope 路线余量④），不做占位增量。
