# 云同步增量：客户端契约提案（v3.7.85）

> 结论先行：**这项不是"客户端再做一版就能上"的东西** —— 现有协议是「全量快照 + last-write-wins」，
> 真正缺的后端能力（增量水位、逐键变更清单、冲突策略）在本仓之外。本文档把**客户端侧能独立完成的
> 部分**与**必须等后端的前置条件**分开列清，作为后端立项时的接口输入；单改客户端不产生任何用户价值
> （只会引入"看似增量、实则丢数据"的假象）。

## 一、现状盘点（客户端，实测口径）

| 项 | 现状 |
|---|---|
| 上行 | `apiPutSnapshot(_buildCloudSnapshot())` —— **全量**键值快照（已排除密钥/本机控制键，v3.7.58） |
| 下行 | `apiGetSnapshot()` → `_applyCloudSnapshot()` —— 覆盖式写入 + 任务按 `updatedAt` 合并（v3.7.80） |
| 冲突 | **last-write-wins**，无冲突检测、无版本号、无操作日志 |
| 保护 | 覆盖前写 `pre_restore_backup` 本机回滚档（v3.7.52） |
| 重试 | 5xx/429 退避 2 次（v3.7.73）；errKind 分类提示（v3.7.71） |
| 成本 | 全量快照随数据线性增长；小改动也要传全量（弱网/移动端体验差） |

## 二、后端需要提供什么（**前置条件，本机不可解**）

1. **增量水位**：客户端上行带 `since=<上次成功同步的水位 token>`；服务端据此返回
   `{ base, changed: [{k, v, ts}], removed: [k...], token: <新水位> }`。
   —— 水位须**单调且服务端权威**（不能用客户端时间戳当水位）。
2. **删除信号**：现行全量协议靠"键消失"表达删除，增量必须有显式 `removed` 列表。
3. **冲突策略开关**（服务端侧）：至少 `lww`（保持现状）与 `mv+提示`（三路合并/冲突清单下发）两档。
4. **幂等键**：同 `token` 重放必须幂等（移动端重试是常态）。

## 三、客户端侧可先行的部分（**可独立完成，不依赖后端**）

| # | 项 | 说明 |
|---|---|---|
| C1 | **本地变更日志** | 写路径（save/setTasks/saveNotes/…）记 `{k, op, ts, h}` 到本地队列；这是增量的"原料"，后端契约一到即可直连 |
| C2 | **上行体积看板** | 诊断面板显示"上次全量快照 X KB / 含 N 键"，让体积问题可见（现状完全黑盒） |
| C3 | **冲突计数** | 下行覆盖时统计"被远端覆盖的本地键"，给用户一个可解释的数字（现状静默 LWW） |
| C4 | **协议开关位** | `cfg.syncIncremental`（默认关）：后端就绪后一开即走增量路径；现在占位不接线 |

> C1–C4 的实现纪律同本仓惯例：**接线点留好、UI 不承诺、守护钉死"开关关闭时行为零变化"**。

## 四、分阶段建议

- **阶段 1（后端未就绪）**：C1 + C2 —— 纯客户端、零协议变更、无用户可见风险。
- **阶段 2（后端契约落地）**：上行切增量（开关制），下行保留全量回退（服务端不支持水位时自动降级）。
- **阶段 3**：C3 冲突计数 + 下行也切增量；两端都按水位，冲突策略由服务端下发。

## 五、为什么现在不写增量代码

- 没有服务端水位实现 → 客户端"增量上行"只能退化为全量（假增量）；
- 冲突策略没定 → 客户端先定 LWW 之外的策略，等于把产品决策埋进协议；
- 历史上本仓已经吃过一次"stub + 活 UI = 虚假功能"的亏（离线AI/ML预测等 4 子系统，v3.7.58 清仓）。
  宁可**如实记账**（本文档 + product-scope 路线余量④），不做占位增量。
