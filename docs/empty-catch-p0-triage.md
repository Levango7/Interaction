## 二、两处判定器误判（尺子的问题，不是代码的问题）

| 位置 | 实际代码 | 为什么被误判 |
|---|---|---|
| `ui-ge-integrations.js:246` | `.catch` 内有 `pushDiag("error", "integration persist seal", {op:"persist_seal"})` | 外层 `.catch(function(e){…})` 被认成「空 catch」 |
| `ui-backup-stats.js:401` | `.then(async…)` + `.catch(function(e){ …pushDiag("warn","备份：图片键读取失败…") })` | 同上（R-37 台账已记过一次） |

**根因定位**：`scripts/lib/empty-catch.mjs` 的 `findEmptyCatches()` 把这类
「Promise 链上的 `.catch(有内容)`」判定为空；随后 `classify(tryBody)` **只看 try 块正文**
（含 `await` / `localStorage` / `JSON.parse` 即判 P0），**不看 catch 里有没有留痕**。
两个环节任一单看都合理，合起来就产生假阳性。

**为什么不在这轮改**（诚实交代）：
1. 改它会**一次性改变全仓判定**（625 处空 catch 全部重判），P0 计数可能从 32 骤降 —— 那才是真实数字，
   但需要单独一轮做「改前/改后逐文件对比」，确认降下去的都是「catch 确有留痕」而不是漏掉真 P0；
2. 现有 7 个测试文件里有**多处精确断言**（如「`ai-tools` 必须恰好 8 处」「`ui-backup-stats` 必须 3 处」
   「`ui-ge-api:63` 必须 1 处」），改尺子会让它们同时失效，必须逐条重新校准 —— 那是独立一笔，不能捎带；
3. 半改的门禁比不改更危险：断言红了没人知道是「代码退化」还是「尺子换了」。

⇒ **已立为待办**（见第五节），不在这轮动。
